# UI 实现与质量验证专项规范

适用：Vibe Coding、前端实现、现有 UI 改造、组件重构和交付检查。

## 1. 实现前检查
- 阅读项目结构、包管理器、框架、路由、样式体系和现有组件。
- 找到现有设计 Token、字体、图标库、主题和可复用组件。
- 确认当前任务的边界与必须保留的功能。
- 未经必要性判断，不要引入新依赖、替换技术栈或重写无关代码。
- 信息不足但可合理推进时，明确假设；不要反复追问非关键细节。

## 2. 代码与样式
- 组件职责清晰，命名能表达用途。
- 复用重复模式，但不要为了抽象而过度泛化。
- 颜色、间距、字号、圆角和状态优先使用统一 Token。
- 避免大量内联样式、`!important`、重复组件和互相冲突的 CSS 覆盖。
- 保护已有业务逻辑、数据流、导航与状态管理。
- 不创建看似可用但没有行为的按钮、菜单、筛选器或开关。
- 若后端能力不存在，不要伪装成功；应说明当前限制或实现合理的本地状态。

## 3. 视觉验证
在工具条件允许时，运行项目并检查实际渲染，而不只阅读源码。
- 检查常见视口尺寸与关键断点。
- 检查对齐、溢出、截断、滚动、弹层位置和固定元素遮挡。
- 检查长文本、空数据、错误提示和加载状态。
- 对比设计目标与实际结果，优先修复层级、间距、可读性和交互问题，而不是继续添加装饰。

## 4. 功能验证
按任务风险检查：
- 主要按钮、链接、导航和菜单。
- 表单验证、提交中状态、成功与失败反馈。
- 筛选、排序、分页、切换和批量操作（若适用）。
- 撤销、取消、重试和数据保留（若适用）。
- 键盘操作、焦点顺序与 Escape/返回行为。
- 控制台错误、构建错误和必要的自动化测试。

## 5. 可访问性验证
- 检查语义元素、标签、替代文本和控件名称。
- 检查键盘焦点是否可见、操作顺序是否合理。
- 检查文本与控件对比度。
- 检查是否仅靠颜色传递状态。
- 尊重减少动态效果与字体缩放等系统偏好。

## 6. 诚实交付
交付时简洁说明：
- 实际完成了什么。
- 哪些关键流程已验证，以及采用了什么验证方式。
- 哪些内容尚未运行或验证。
- 是否存在已知限制。

绝不能声称运行了未实际运行的命令、测试或浏览器检查。静态阅读、成功构建和完整交互验证是不同等级的证据，不应混为一谈。
